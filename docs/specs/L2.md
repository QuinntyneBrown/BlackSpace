## L1-11: Member Signup API

### L2-11.1: Member Entity and DTOs
Create a `Member` entity with properties: Id (Guid), FullName (string, required), Email (string, required, unique), RoleTitle (string, nullable), Organization (string, nullable), ReferralSource (string, nullable), CreatedAtUtc (DateTime), and IpAddress (string, nullable). Create `CreateMemberRequest` and `MemberResponse` DTOs.
**Acceptance Criteria:** The Member entity maps correctly to the database. DTOs serialize/deserialize correctly in JSON. A unit test validates the entity-to-DTO mapping.

### L2-11.2: POST /api/members Endpoint
Implement a POST /api/members endpoint that accepts `CreateMemberRequest` JSON body, validates it using FluentValidation (FullName required, max 200 chars; Email required, valid format, max 254 chars; optional fields max 200 chars), creates a Member record, and returns 201 Created with the `MemberResponse` body and a Location header.
**Acceptance Criteria:** An integration test POSTs valid member data and receives 201 with correct response body. The member exists in the database after the call.

### L2-11.3: Duplicate Email Detection
If a POST /api/members request contains an email that already exists in the database (case-insensitive comparison), return 409 Conflict with a JSON error body: `{"error": "already_registered", "message": "This email is already part of the community."}`.
**Acceptance Criteria:** An integration test POSTs the same email twice. The first returns 201, the second returns 409 with the correct error body.

### L2-11.4: Validation Error Responses
If validation fails, return 422 Unprocessable Entity with a JSON body: `{"error": "validation_failed", "message": "Please fix the errors below.", "errors": {"fieldName": ["error message"]}}`. The response follows RFC 7807 problem details pattern.
**Acceptance Criteria:** An integration test POSTs invalid data (empty name, invalid email) and receives 422 with field-level error messages.

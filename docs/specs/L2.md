## L1-1: Hero Section

### L2-1.1: Desktop Hero Layout (≥1024px)
The hero section occupies the full viewport width and height. Headline "Black Canadians in Space & Defence" is large (48–64px), centered. Subheadline sits below at 18–20px. Two buttons horizontally aligned: "Join the Community" (primary, filled) and "Learn More" (secondary, outlined). Background is deep navy/black with subtle gradient or star-field texture.
**Acceptance Criteria:** Desktop frame shows a full-width hero with centered headline, subheadline, and two horizontally-aligned CTA buttons on a dark space-themed background. All content is above the fold at 1440×900.

### L2-1.2: Tablet Hero Layout (768–1023px)
Same content as desktop but headline scales to 36–44px. Buttons remain horizontal. Padding adjusts for narrower viewport.
**Acceptance Criteria:** Tablet (768px) frame shows the hero with appropriately scaled typography and maintained horizontal button layout.

### L2-1.3: Mobile Hero Layout (<768px)
Headline scales to 28–36px. Subheadline to 16px. Buttons stack vertically, full-width. Content remains centered and above the fold on a 375px-wide screen.
**Acceptance Criteria:** Mobile (375px) frame shows stacked buttons, scaled-down text, and all hero content visible without scrolling.

# Backend API Requirements

## L1-10: .NET Solution Structure & Configuration

### L2-10.1: Solution and Project Structure
Create a .NET 9 solution at `src/BlackSpace.Api/` with four projects: `BlackSpace.Api` (ASP.NET Core Web API using Minimal APIs), `BlackSpace.Domain` (class library for entities, DTOs, interfaces), `BlackSpace.Infrastructure` (class library for EF Core DbContext, repositories, email service), and `BlackSpace.Tests` (xUnit test project). All projects target .NET 9.
**Acceptance Criteria:** `dotnet build` succeeds on the solution. The solution contains 4 projects with correct references: Api → Domain + Infrastructure, Infrastructure → Domain, Tests → Api + Domain + Infrastructure.

### L2-10.2: Dependency Injection & Configuration
Configure DI for all services (DbContext, repositories, email service) in Program.cs. Use `appsettings.json` and `appsettings.Development.json` for environment-specific config including database connection string, SMTP settings, CORS origins, and LinkedIn group URL.
**Acceptance Criteria:** The application starts without errors. All services resolve correctly from the DI container. Configuration values are read from appsettings files.

### L2-10.3: CORS Configuration
Configure CORS to allow the Angular frontend (localhost:4200 in development, configurable production origin) to make requests. Allow GET, POST, OPTIONS methods and standard headers.
**Acceptance Criteria:** An integration test confirms that CORS headers are present on API responses for allowed origins. Requests from disallowed origins are rejected.

## L1-11: Member Signup API

### L2-11.1: Member Entity and DTOs
Create a `Member` entity with properties: Id (Guid), FullName (string, required), Email (string, required, unique), RoleTitle (string, nullable), Organization (string, nullable), ReferralSource (string, nullable), CreatedAtUtc (DateTime), and IpAddress (string, nullable). Create `CreateMemberRequest` and `MemberResponse` DTOs.
**Acceptance Criteria:** The Member entity maps correctly to the database. DTOs serialize/deserialize correctly in JSON. A unit test validates the entity-to-DTO mapping.

### L2-11.2: POST /api/members Endpoint
Implement a POST /api/members endpoint that accepts `CreateMemberRequest` JSON body, validates it using FluentValidation (FullName required, max 200 chars; Email required, valid format, max 254 chars; optional fields max 200 chars), creates a Member record, and returns 201 Created with the `MemberResponse` body and a Location header.
**Acceptance Criteria:** An integration test POSTs valid member data and receives 201 with correct response body. The member exists in the database after the call.

### L2-11.3: Duplicate Email Detection
If a POST /api/members request contains an email that already exists in the database (case-insensitive comparison), return 409 Conflict with a JSON error body: `{"error": "already_registered", "message": "This email is already part of the community."}`.
**Acceptance Criteria:** An integration test POSTs the same email twice. The first returns 201, the second returns 409 with the correct error body.

### L2-11.4: Validation Error Responses
If validation fails, return 422 Unprocessable Entity with a JSON body: `{"error": "validation_failed", "message": "Please fix the errors below.", "errors": {"fieldName": ["error message"]}}`. The response follows RFC 7807 problem details pattern.
**Acceptance Criteria:** An integration test POSTs invalid data (empty name, invalid email) and receives 422 with field-level error messages.

## L1-12: Email Service Integration

### L2-12.1: IEmailService Interface and Welcome Email
Define `IEmailService` with a `SendWelcomeEmailAsync(Member member)` method. Implement `SmtpEmailService` that sends a templated HTML welcome email via SMTP with subject "Welcome to Black Space Canada", containing the member's name, LinkedIn group link, and next meetup details. Implement `ConsoleEmailService` for development that logs email content to the console.
**Acceptance Criteria:** A unit test with a mock verifies that `SendWelcomeEmailAsync` is called after successful member creation. The ConsoleEmailService logs the email subject and recipient.

### L2-12.2: Email Dispatch on Signup
After a successful member creation in POST /api/members, dispatch the welcome email asynchronously (fire-and-forget with error logging). Email failures must not cause the signup to fail — the member is still created and 201 is returned.
**Acceptance Criteria:** An integration test confirms that a member is created (201) even when email sending throws an exception. The error is logged.

## L1-14: Health & Observability

### L2-14.1: Health Check Endpoint
Implement GET /api/health using ASP.NET Core health checks. Include a database connectivity check. Return 200 with `{"status": "Healthy"}` when all checks pass, 503 when unhealthy.
**Acceptance Criteria:** An integration test GETs /api/health and receives 200 with status "Healthy".

### L2-14.2: Structured Logging with Serilog
Configure Serilog with console sink and structured JSON output. Log all incoming requests (method, path, status code, duration). Log member signups and email dispatch results at Information level. Log errors at Error level.
**Acceptance Criteria:** Application starts with Serilog configured. A test verifies that Serilog is registered as the logging provider.

### L2-14.3: Swagger/OpenAPI Documentation
Configure Swagger UI at /swagger and OpenAPI spec at /swagger/v1/swagger.json. All endpoints have summary descriptions and response type annotations.
**Acceptance Criteria:** An integration test GETs /swagger/v1/swagger.json and receives a valid OpenAPI document containing all endpoint paths.

## L1-15: API Integration Tests

### L2-15.1: Test Infrastructure
Create a `CustomWebApplicationFactory<T>` that configures an in-memory SQLite database, replaces the email service with a test double, and provides helper methods for common test operations (creating members, asserting responses).
**Acceptance Criteria:** The test factory creates a working test server. A simple test GETs /api/health and receives 200.

### L2-15.2: Full Endpoint Coverage
Write integration tests covering: successful member creation, duplicate email rejection, validation errors (missing name, invalid email, field too long), stats endpoint accuracy, referral sources list, health endpoint, and Swagger availability.
**Acceptance Criteria:** All tests pass. `dotnet test` reports 0 failures. Every API endpoint has at least one test.
